PostgreSQL 与 MySQL 对比

PostgreSQL 与 MySQL 对比

1. 基本定位与适用边界

维度 PostgreSQL 16/17 MySQL 8.x 较稳的判断
数据库类型 对象关系型数据库（ORDBMS），扩展类型能力突出 以关系型数据库为主，InnoDB 是默认事务存储引擎 PG 类型系统和扩展机制更强
标准契合度 SQL 标准契合度和高级 SQL 特性通常更好 8.x 已支持 CTE、窗口函数、表达式索引等，但高级 SQL 生态仍常弱于 PG 复杂 SQL 场景 PG 更顺
设计取向 功能完备、类型丰富、可定制、约束表达强 简单、直接、部署广泛、Web OLTP 成熟 “强弱”应转译为业务适配度
版本现状 PG 16/17 功能和并行能力继续增强 MySQL 8.x 是当前主流，8.4/LTS 和 9.x 生态在演进 新项目应以各自当前稳定版本为准

2. 数据类型与建模能力

能力 PostgreSQL MySQL/InnoDB 判断
基础类型 数值、文本、时间、布尔、网络地址、UUID、几何、数组、范围、枚举等很丰富 数值、字符串、日期时间、JSON、空间类型等足够覆盖常见 Web 业务 PG 建模表达力更强
数组/范围/复合类型 原生支持，适合标签、区间、权限范围、复杂值对象 常用关联表、JSON 或应用层拆解替代 PG 可减少某些反范式和折衷建模
自定义类型/操作符 支持自定义类型、操作符、函数、索引方法 能力边界主要不是“用户自定义核心类型” PG 明显更强
严格约束 CHECK、外键、唯一约束、排他约束、部分唯一索引能力强 支持外键、唯一键、CHECK 等；触发器和 SQL 表达能力可覆盖大部分需求 对数据完整性要求越高，PG 越有优势
SERIAL / 自增与标识列 支持 IDENTITY 和 sequence AUTO_INCREMENT 成熟 均可用；迁移时注意主键生成语义
时间类型 TIMESTAMP、TIMESTAMPTZ、INTERVAL、DATE 等语义清晰 DATETIME、TIMESTAMP 行为受时区、范围和默认值影响，需仔细设计 跨时区系统 PG 更省心

3. JSON 与半结构化数据

能力 PostgreSQL MySQL 8.x 判断
类型 json 保存原始文本；jsonb 使用二进制表示，支持去重、索引和丰富操作符 JSON 是带校验和优化存储格式的二进制类型 两者都不是“纯文本”；PG 的操作符/索引生态通常更完整
索引 GIN、表达式索引、部分索引可组合，适合路径/存在性/包含查询 可使用生成列 + 普通/函数索引；MySQL 也支持 JSON_VALUE 等函数路径，但灵活性弱于 PG PG 更强，MySQL 可以用“JSON + 生成列”补齐高频路径
语义 JSONB 适合读多、复杂过滤和索引；json 适合保留原文和键序 JSON 原地更新和部分更新有实现边界，需要看具体语句和版本行为 PG 更适合把 JSON 当一等建模工具
风险 JSONB 索引和旧版本清理也有成本；不要把所有字段都塞进 JSON 生成列设计不好会带来存储/写放大；复杂 JSON 查询仍易失控 半结构化数据也要建模，不是“扔 JSON”就结束

4. SQL、查询与分析能力

能力 PostgreSQL MySQL 8.x 判断
CTE 支持 WITH、递归 CTE、物化提示（不同版本行为有差异） 8.0 起支持 CTE 和递归 CTE 均可用，PG 高级用法更丰富
窗口函数 支持完整，帧、聚合、排名和复杂分析表达好 8.0 起支持窗口函数 均可用；PG 高级组合更强
LATERAL 支持成熟 8.0.14 起支持 LATERAL 派生表 均可用，PG 更常见
并行查询 支持顺序扫描、索引扫描、join、聚合等并行路径 8.x 有并行读、并行聚合等能力 双方都可调优；不要只看营销指标
物化视图 原生物质化视图，可手动/调度刷新 无原生物化视图，常用表 + 任务、生成表或外部层模拟 分析场景 PG 更直接
查询规划器 统计信息和高级 join/扫描路径能力强 8.x 优化器比旧版进步明显，但复杂 SQL 的表达和优化空间通常仍小于 PG 复杂报表/分析 PG 更合适
外部数据/联邦能力 FDW 生态较丰富 原生联邦能力有限，通常靠应用层、中间件或复制 跨源分析 PG 生态更好

5. 事务、并发与锁

能力 PostgreSQL MySQL/InnoDB 判断
ACID 单机事务和约束保障成熟 InnoDB 提供 ACID；MyISAM 不支持事务，生产核心表不建议使用 两者核心路径都能支撑关键业务
MVCC 旧版本由表内历史版本 + VACUUM 清理；长事务会阻碍清理 undo log/回滚段维护历史版本；长查询会带来 undo 增长和读视图代价 都有长事务风险，只是表现形式不同
读阻塞 普通 SELECT 与写入不互相阻塞 普通 SELECT 与写入也不互相阻塞 “写不阻塞读”不是 PG 独有优势
隔离级别 READ COMMITTED、REPEATABLE READ、SERIALIZABLE；默认 READ COMMITTED READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ、SERIALIZABLE；默认 REPEATABLE READ 不要靠默认隔离级别判断业务正确性，必须显式设计
锁与热点 行锁、咨询锁、并发索引创建等成熟；热点行更新需重点设计 行锁成熟；热点行、间隙锁和死锁要结合隔离级别与索引设计处理 热点行为取决于事务形状，不取决于品牌
长事务风险 阻碍 VACUUM，可能导致表/索引膨胀和事务 ID 回卷压力 undo 增长、历史链变长、查询退化，复制和恢复也要注意 监控和治理长事务是两边共同要求

6. 性能：必须按负载拆开看

负载形状 PostgreSQL 的表现条件 MySQL/InnoDB 的表现条件 可用判断
简单点查/简单 CRUD PG 16/17 已很强；连接模型、连接池、索引和缓存决定结果 常见 Web 场景成熟，8.x 优化明显 不能默认 MySQL 更快，应实测
读多写少 Web 业务 索引设计好时表现稳定 生态成熟，托管服务和工具链完善 MySQL 是合理默认之一
写密集批量导入 COPY、UNLOGGED 表、批量事务、合理索引策略可达高吞吐 LOAD DATA、批量 INSERT、innodb_autoinc_lock_mode 等有成熟路径 都能做，重点在批量大小、索引延迟创建、提交策略
高并发热点更新 避免单行热点、缩短事务、合理重试；索引膨胀要监控 行锁成熟，热点行、间隙锁、死锁需按索引和隔离级别调优 热点更新两边都要拆分竞争
复杂查询/报表 优化器、窗口函数、CTE、物化视图、并行能力组合更强 复杂 SQL 可用，但高级分析和物化视图生态弱一些 PG 通常更顺
全内存点查 连接/进程模型和池化方案影响显著 简单查询路径成熟，托管场景表现稳定 应按真实 QPS、CPU、连接数实测

性能验证最低清单

  1. 用真实或脱敏后的生产形数据测，不要只测单表百万行均匀随机数据。
  2. 同时记录 P50/P95/P99、TPS/QPS、CPU、I/O、锁等待、上下文切换和连接队列。
  3. 测“正常路径”和“故障/边界路径”：长事务、大批量导入、索引创建、备份、主从切换。
  4. 控制变量：连接池、事务大小、隔离级别、索引、EXPLAIN ANALYZE、缓冲池/shared buffers、WAL/binlog 配置。
  5. 给出运行边界：目标数据量增长、并发连接、备份窗口、可接受主从延迟、恢复时间目标。

7. 全文搜索、GIS 与向量搜索

能力 PostgreSQL MySQL 8.x 判断
全文搜索 内置全文检索，支持配置词典、rank、索引，复杂中文方案可结合扩展/外部搜索 内置全文索引可用于基础场景，中文分词和高级检索能力有限 重搜索选 PG 或专业搜索引擎
GIS PostGIS 是行业级开源空间扩展，函数、投影、地理类型和空间索引生态强 原生空间类型和函数覆盖基础场景，复杂 GIS 能力远不如 PostGIS 专业 GIS 明确优先 PG/PostGIS
向量搜索 需要 pgvector 等扩展；可支持向量类型、距离运算和索引，生态活跃 需看具体版本、发行版或云扩展；传统 MySQL 社区版原生向量能力不是同等成熟选项 原句应为“PG + 合适扩展”，不要说 PG 原生就带向量
专业搜索替代 PG 能处理中小规模应用内搜索 MySQL 也能处理基础场景 大规模、复杂相关性、分词和实时索引应考虑 OpenSearch/Elasticsearch/专用引擎

8. 高可用、复制与扩展架构

能力 PostgreSQL MySQL/InnoDB 判断
复制基础 物理流复制、逻辑复制；WAL 是核心机制 binlog 主从复制、GTID、半同步等成熟 两者都能支撑高可用，方案成熟度不同
同步语义 同步/异步流复制可配置 异步复制是常见默认；半同步可提升持久性但影响写延迟 RPO/RTO 必须显式设计
多主 原生不推荐做多主；BDR 等属第三方方案 InnoDB Cluster/Group Replication、NDB、第三方拓扑有不同取舍 不要把“多主”当默认优势
故障切换 Patroni、repmgr、云托管自动切换等生态成熟 Orchestrator、InnoDB Cluster、云托管切换等方案成熟 团队熟悉度和演练频率比组件列表更重要
读写分离 逻辑复制/流复制 + 应用层或代理 binlog 复制 + 代理/应用层方案广泛 复制延迟和一致性语义要进接口设计
分库分表 Citus、分区表、FDW、外部中间件等路线 InnoDB 分区、MySQL 生态分库分表组件多 超大规模分布式是架构问题，不是单一数据库开关

9. 生态、运维与成本

维度 PostgreSQL MySQL/InnoDB 判断
部署 单二进制/服务概念清晰，云托管和容器生态成熟 安装、托管、容器和云产品普及度高 两边都不难；难点在参数、备份、监控和演练
监控重点 锁等待、长事务、连接、缓存命中率、VACUUM、事务 ID 年龄、复制延迟、表/索引膨胀 锁等待、死锁、长事务、undo/历史链、连接、缓冲池、复制延迟、binlog 和慢查询 监控项不同，不等于某一边成本必然更低
PostgreSQL 特有风险 长事务阻碍清理；VACUUM 不足导致膨胀；事务 ID 回卷；参数和索引膨胀治理 存储引擎差异；主从延迟和故障切换一致性；热点页/热点行；binlog 与备份恢复链条 “PG 一定更难运维”太绝对
MySQL 特有风险 不适用 现代版继续收敛，但老资料常把 MyISAM、查询缓存等旧行为混入当前架构 生产核心表应锁定 InnoDB 和当前稳定版本
备份恢复 pg_basebackup、WAL 归档、逻辑备份、快照、云托管 PITR mysqldump、MySQL Enterprise Backup、XtraBackup、binlog PITR、快照、云托管 PITR 按恢复目标设计，不只备份文件
商业支持 社区 + 云厂商 + EDB/专业服务 Oracle、Percona、云厂商、托管服务广泛 两边商业支持都比老文章描述的更成熟
人才与工具 后端/DBA 人才增多，云原生项目占比上升 Web 后端、托管服务、存量工具链极大 团队经验优先级很高
许可证 PostgreSQL License，商业集成边界宽松 GPL/商业双许可，发行版和服务边界要理解清楚 商业产品集成时必须做法务确认

10. 典型场景建议

场景 更合适的默认 理由 仍需确认
经典 Web/CRUD、内容站、电商订单主库 MySQL 8.x 团队熟悉度、托管生态、简单 OLTP 成熟 热点 SKU、库存扣减、隔离级别、死锁和重试
SaaS 中后台、复杂业务建模、强约束业务 PostgreSQL 复杂类型、约束、高级 SQL、扩展机制有利 多租户隔离模型、索引规模、连接池
报表/BI/复杂分析 PostgreSQL 或专业分析库 CTE/窗口函数/物化视图/复杂 join 更顺 数据增长后应评估列存、数仓或湖仓
GIS PostgreSQL + PostGIS 空间函数、投影、索引和行业生态最强 数据量、瓦片/轨迹负载、是否叠加专业 GIS 服务
全文搜索 PostgreSQL 或专用搜索引擎 PG 可覆盖中小场景，大搜索规模需要专用引擎 分词、相关性、更新频率、QPS
向量搜索 PostgreSQL + pgvector 或专用向量库 pgvector 生态活跃，PG 便于混合检索 维度、召回、QPS、索引内存、是否需要专用 ANN 系统
金融核心/强一致交易系统 都可能，但必须专项设计 一致性来自事务、隔离级别、复制语义、审计和恢复设计 RPO/RTO、审计、对账、跨服务事务边界
高并发写入/日志/事件流 先评估专用写入/队列/时序系统 通用库不应默认吞下无边界写入流 分区、保留策略、压缩、消费链路
多租户 SaaS PostgreSQL 或 MySQL 都可行 关键在租户隔离、迁移、容量和合规 schema 隔离、行级隔离、资源隔离、 noisy neighbor
存量 MySQL 系统 不因“PG 更先进”贸然替换 迁移成本、SQL 方言、ORM、存储过程、运维链路都会放大风险 先做 SQL/依赖审计和灰度迁移方案

11. 迁移与兼容风险

项目 MySQL → PostgreSQL PostgreSQL → MySQL 通用风险
SQL 方言 引号、类型、日期函数、UPSERT、分页、分组严格性差异大 序列/数组/JSONB/高级 SQL 难替代 ORM 生成的 SQL 也会绑定方言
默认行为 大小写折叠、空串/null、类型隐转、时间时区行为不同 大小写、排序规则、时区、默认值语义不同 必须做行为对齐测试，不只看语法通过
主键/序列 AUTO_INCREMENT 到 sequence/identity 的迁移要注意间隙和缓存 sequence 到 AUTO_INCREMENT 要处理起始值和并发 迁移期间要冻结写入或做双向核对
JSON JSON/生成列到 jsonb 时要重新评估路径、索引和更新 JSONB 操作符/索引到 MySQL 要重写 JSON 不能当成透明迁移
存储过程/触发器 PL/pgSQL 与 MySQL 存储过程差异大 反向迁移也需重写 尽量减少数据库内复杂业务逻辑
工具 pgloader、ETL、云迁移服务 ETL、云迁移服务 迁移工具不能替代语义验证

迁移流程建议

  1. 先审计：列出对象、数据量、依赖、存储过程、触发器、ORM 方言、慢 SQL、报表、备份和高可用链路。
  2. 行为验证：为边界数据、并发事务、错误路径、空值、时区、排序、大小写、JSON、主键生成写对齐测试。
  3. 性能基线：保留源库 P95/P99、慢 SQL、硬件和参数，迁移后在同负载下对比。
  4. 双轨方案：只读灰度、影子库、双写/对账、按模块迁移或按只读服务迁移，避免一次性大切换。
  5. 回退设计：明确回滚点、数据补偿、DNS/连接切换、复制方向、停写窗口和验证人。
  6. 上线后观察：监控锁、长事务、膨胀/undo、复制延迟、慢 SQL、错误率和业务对账结果。

12. 选型决策清单

先回答下面的问题，再决定默认库：

  1. 新项目还是已有系统？已有系统的迁移成本必须计入。
  2. 最关键的 20 条 SQL 是什么？事务、索引和并发形状是什么？
  3. 是否有复杂类型、数组、范围、GIS、JSON、向量、全文搜索需求？
  4. 期望一致性语义是什么？可接受复制延迟和故障丢失窗口是多少？
  5. P95/P99、TPS/QPS、数据量三年增长、备份窗口和恢复目标是什么？
  6. 团队当前最熟悉哪一个？有没有 24 小时值班和故障演练能力？
  7. 是否使用云托管？托管服务是否覆盖自动备份、监控、参数调优、切换、审计和合规？
  8. 未来 5 年是更可能扩大 OLTP、增加报表、引入搜索/向量，还是先保交付？
  9. 是否存在合规、数据驻留、审计、许可证或商业支持要求？
  10. 如果数据库不可用 30 分钟，业务损失和恢复路径是什么？

13. 可执行的选型规则

  • 默认 MySQL：新团队、经典 CRUD、读多写少、急需上线、已有 MySQL 托管和运维体系、无复杂 SQL/类型需求。
  • 默认 PostgreSQL：复杂领域建模、强约束、丰富类型、JSONB、GIS、pgvector、复杂报表、SaaS/ToB 中后台、愿意学习 PG 运维模型。
  • 不要只因“性能”切换：除非有真实负载基线，且新库在关键路径上稳定超过阈值。
  • 不要只因“功能多”切换：功能只在团队能正确使用、运维能监控其代价时才是收益。
  • 数据库不是孤岛：连接池、缓存、队列、搜索引擎、数仓、备份、故障演练和应用架构共同决定成败。
  • 保留演进路径：优先把业务逻辑放在可迁移层，避免大量私有 SQL、触发器和存储过程把系统焊死在单一数据库上。

14. 常见误区修正

误区 更准确的表述
PostgreSQL 有 MVCC，MySQL 没有 两者都用 MVCC。InnoDB 依赖 MVCC；PG 和 InnoDB 的版本存储与清理机制不同
MySQL JSON 只是文本 MySQL JSON 有校验和优化二进制存储；PG JSONB 的索引和操作符生态通常更强，但两者定位不同
MySQL 8 仍有查询缓存 MySQL 8.0 已移除查询缓存，不应继续作为当前架构核心层
PG 天然适合高并发写 PG 能支撑写密集负载，但热点行、长事务和膨胀必须治理；MySQL 也有成熟写路径
MySQL 天然只适合简单读 MySQL 8.x 支持窗口函数、CTE、JSON、表达式索引等；能否支撑复杂业务要看设计和版本边界
PG 所有云投入都超过 MySQL 云厂商对两者都有重点投入；具体能力要看托管版本、参数开放度、备份/恢复、监控和切换 SLA
学习成本 PG 一定更高 初学 CRUD 时 MySQL 常更容易；掌握生产级调优、备份、恢复和高可用时，两边都需要专业能力
“不换数据库”等于选 PG 长期可控来自数据模型、约束、监控、备份、迁移策略和团队认知，不是单次选型

15. 最后选型建议

  • 经典 Web/CRUD、读多写少、已有 MySQL 生态、团队经验集中：MySQL 8.x 仍然合理。
  • 复杂关系建模、复杂 SQL、约束校验、GIS、丰富 JSON/半结构化数据、扩展类型、搜索与向量扩展生态：PostgreSQL 通常更合适。
  • 性能不能靠品牌判断。简单 OLTP 不等于 MySQL 必胜；复杂查询也不等于 PostgreSQL 必胜。必须看表结构、索引、事务模式、连接池、数据量、并发形状和硬件。
  • 运维难点不同：PostgreSQL 重点在 VACUUM、事务 ID 回卷、长事务和膨胀控制；MySQL/InnoDB 重点在存储引擎边界、复制拓扑、主从延迟、故障切换和参数调优。

不要问“PostgreSQL 和 MySQL 谁更强”，改成问：

  1. 这套业务的关键事务长什么样？
  2. 哪些数据必须强约束，哪些适合 JSON/半结构化？
  3. P95/P99、并发、增长和故障恢复目标是什么？
  4. 团队能长期运维哪个数据库？
  5. 迁移、备份、监控、审计和扩展路径是否已经设计？

如果答案清楚，PostgreSQL 和 MySQL 都是优秀选择；如果答案不清楚，换数据库本身救不了设计问题。
