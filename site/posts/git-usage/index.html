Git 使用

0.什么是Git

Git是分布式版本控制系统，那么它就没有中央服务器的，每个人的电脑就是一个完整的版本库，这样，工作的时候就不需要联网了，因为版本都是在自己的电脑上。既然每个人的电脑都有一个完整的版本库，那多个人如何协作呢？比如说自己在电脑上改了文件A，其他人也在电脑上改了文件A，这时，你们两之间只需把各自的修改推送给对方，就可以互相看到对方的修改了。

6.✨branch分支管理

基本操作

使用分支意味着你可以从开发主线上分离开来，然后在不影响主线的同时继续工作。

  • 创建分支：
1git branch [branchname]

单单使用git branch的时候是列出分支。当你执行 git init 的时候，默认情况下 Git 就会为你创建 master 分支。

  • 切换分支
1git checkout [branchname]

当你切换分支的时候，Git 会用该分支的最后提交的快照替换你的工作目录的内容， 所以多个分支不需要多个目录。

我们也可以使用git checkout -b (branchname)命令来创建新分支并立即切换到该分支下，从而在该分支中操作。

  • 合并分支
1git merge [branchname]
2
3git merge --ff-only dev

一旦某分支有了独立内容，你终究会希望将它合并回到你的主分支。 你可以使用上面的命令把这个分支合并到master分支。

--ff-only 的好处是：如果不能干净快进，它会直接停住，不给你制造意外的 merge commit。

  • 删除分支
1git branch -d [branchname]

合并并不仅仅是简单的文件添加、移除的操作，Git也会合并修改。我们可以用 git add 要告诉 Git 文件冲突已经解决。

  • 查看分支
1git branch -v

常见命令：

命令 效果
git branch -v 本地分支 + 提交信息
git branch -vv 本地分支 + 提交信息 + 上游跟踪关系
git branch -a 本地 + 远程分支（只显示分支名）
git branch -av 本地 + 远程分支 + 提交信息
git branch -avv 本地 + 远程分支 + 提交信息 + 上游关系
git branch -r 只显示远程分支名
git branch -rv 远程分支 + 提交信息

跟踪分支

1# 1. 先 fetch 远程所有更新（包括 common-rag）
2git fetch origin
3
4# 2. 查看远程分支情况
5git branch -r | grep [branchname]

修改分支名字

  1. 切换到要重命名的分支（如果当前就在该分支，可直接执行下一步）：
1git checkout [master]
  1. 执行重命名命令：
1git branch -m [main]

更新远程仓库

  1. 推送新分支到远程并建立跟踪关系：
1git push -u origin [main]
  1. 删除旧的远程分支（可选，但建议执行以避免混淆）：
1git push origin --delete [master]
  1. 删除本地跟踪分支（可选） 删除远程分支不会自动移除本地跟踪引用，可用以下命令清理：
1# 删除本地跟踪分支
2git branch -d [master]
3
4# 或同步并清理已失效的远程引用
5git fetch -p

注意事项

  • 删除前确认该分支已合并或不再需要，避免丢失重要代码。
  • 本地和远程分支是独立的，删除一方不会影响另一方。
  • 对未合并的分支，建议先备份或确认无用再执行删除操作。

这样，你就可以安全、干净地管理 Git 远程分支了。

远程仓库管理 remote

git remote 命令用于用于管理 Git 仓库中的远程仓库。

git remote 命令提供了一些用于查看、添加、重命名和删除远程仓库的功能。

以下是 git remote 命令的常见用法：

  • git remote：列出当前仓库中已配置的远程仓库。
  • git remote -v：列出当前仓库中已配置的远程仓库，并显示它们的 URL。
  • git remote add <remote_name> <remote_url>：添加一个新的远程仓库。指定一个远程仓库的名称和 URL，将其添加到当前仓库中。
  • git remote rename <old_name> <new_name>：将已配置的远程仓库重命名。
  • git remote remove <remote_name>：从当前仓库中删除指定的远程仓库。
  • git remote set-url <remote_name> <new_url>：修改指定远程仓库的 URL。
  • git remote show <remote_name>：显示指定远程仓库的详细信息，包括 URL 和跟踪分支。

以下列出了远程仓库、添加远程仓库、重命名远程仓库、删除远程仓库、修改远程仓库 URL 和查看远程仓库信息的用法：

1git remote
2git remote -v
3
4git remote add origin https://github.com/user/repo.git
5git remote rename origin new-origin
6git remote remove new-origin
7git remote set-url origin https://github.com/user/new-repo.git
8git remote show origin

7.tag标签

如果你达到一个重要的阶段，并希望永远记住那个特别的提交快照，你可以使用 git tag 给它打上标签。

比如说，我们想为我们的项目发布一个"1.0"版本。 我们可以用 git tag -a v1.0 命令给最新一次提交打上（HEAD）"v1.0"的标签。

-a 选项意为"创建一个带注解的标签"。 不用 -a 选项也可以执行的，但它不会记录这标签是啥时候打的，谁打的，也不会让你添加个标签的注解。 我推荐一直创建带注解的标签。

1git tag -a v1.0

如果我们要查看所有标签可以使用以下命令：

1$ git tag
2v0.9
3v1.0

指定标签信息命令：

1git tag -a <tagname> -m "我是标签"

PGP签名标签命令：

1git tag -s <tagname> -m "我是标签"

1# 在主仓库目录执行
2git worktree add [新目录位置] [使用的分支]
3
4git worktree add ../hotfix-branch hotfix
  1. 在工作树中开发
1cd ../hotfix-branch
2git status --short --branch
3
4git add .
5git commit -m "fix(具体模块): 描述本次修改"
  1. 合并与清理：在主仓库目录完成合并后，清理工作树。
1到主目录合并本地分支 dev、hotfix
2cd [主目录]
3git status --short --branch
4
5# 主目录必须干净；干净后执行
6git merge --ff-only hotfix

别名

User git不是配置时候的user.name，一般只能是 git，如果不配置就会是 user.name 里面配置的内容，但是配合 Host 别名使用的时候机会报错：

如果不配置User，并且 user.name=suhan，那么：

1ssh -T github		=		ssh -T suhan@github.com

1ssh -T gitlab-local =		ssh -T git@10.6.70.125
2ssh -T github		=		ssh -T git@github.com

1Host gitlab 10.6.70.125
2  HostName 10.6.70.125
3  User git
4  IdentityFile ~/.ssh/id_gitlab
5  IdentitiesOnly yes
6  PreferredAuthentications publickey

一台主机下，个人 GitHub 和公司 GitLab 同时使用

方案：基于config文件

原理上就是对 SSH 协议配置 config 文件，对不同的域名采用不同的认证密钥。

配置流程：

  1. 配置 Git 用户名、邮箱
1# 全局配置，Github仓库中默认使用此配置
2git config --global user.name "Voluee"
3git config --global user.email "personal@xxx.com"
4# 团队项目配置，每次新创建一个项目，需要执行下
5git config --local user.name "Voluee"
6git config --local user.email "company@xxx.com"
  1. 生成 ssh key

ssh key 默认生成后保存在 ~/.ssh/目录下 ，分别为id_gitlab和id_github两个文件，由于我们需要分开配置，所以生成 SSH 密钥时，通过 -f 参数指定自定义文件名

1#创建gitlab的SSH-Key
2ssh-keygen -t rsa -C "company@xxx.com" -f ~/.ssh/id_gitlab
3#创建github的SSH-Key
4ssh-keygen -t rsa -C "personal@xxx.com" -f ~/.ssh/id_github

命令执行完成后，这时~/.ssh目录下会多出四个文件，xxx.pub里保存的就是我们要使用的key，这个key就是用来上传到Gitlab和GitHub上的。

  1. 配置 config 文件

在 ~/.ssh目录下，如果不存在，则新建 touch ~/.ssh/config文件。

【注意】文件就叫config，没有后缀。

文件内容添加如下：

1#gitlab
2Host [名字备注]
3	HostName [这里填gitlab真实地址]
4	IdentityFile ~/.ssh/id_gitlab 【这里填写上一步创建得密钥文件 注意要对应上 正式环境删除此段注释】
5	IdentitiesOnly yes 【只使用指定的密钥，防止 SSH 自动尝试其他密钥导致认证混乱】
6    PreferredAuthentications publickey 【跳过密码验证】
7 
8# 例子：
9
10Host github
11	HostName ssh.github.com
12	Port 443
13	IdentityFile ~/.ssh/id_github
14	IdentitiesOnly yes
15    PreferredAuthentications publickey

字段解释：

1Host
2	它涵盖了下面一个段的配置，我们可以通过他来替代将要连接的服务器地址。这里可以使用任意字段或通配符。当ssh的时候如果服务器地址能匹配上这里Host指定的值，则Host下面指定的HostName将被作为最终的服务器地址使用，并且将使用该Host字段下面配置的所有自定义配置来覆盖默认的/etc/ssh/ssh_config配置信息。
3Port
4	自定义的端口。默认为22，可不配置
5User
6	自定义的用户名，默认为git，可不配置
7HostName
8	真正连接的服务器地址
9PreferredAuthentications
10	指定优先使用哪种方式验证，支持密码和秘钥验证方式

代码回滚

在使用 Git 时，如果需要丢弃本地的修改，可以根据修改的状态选择不同的方法。以下是几种常见场景及对应的解决方法：

1. 已使用 git add 缓存代码，但未提交

如果修改已被添加到暂存区，但尚未提交，可以先将其从暂存区移除，然后再撤销：

  • 移除暂存区中的文件：
1git reset HEAD 文件名
  • 移除所有暂存区中的文件：
1git reset HEAD

此时，文件会回到工作区状态，接着可以使用第一种方法 (git checkout) 丢弃修改。

2. git commit后

修改了本地的代码，然后使用：

1git add file
2git commit -m '修改原因'

执行commit后，还没执行push origin时，想要撤销这次的commit，该怎么办？

  • HEAD 回退 1 个 commit，即撤销最近的一次提交：
1git reset HEAD~1
2#或者
3git reset HEAD^

默认是 --mixed 模式，不会删除工作区的修改，只会把暂存区（index）的内容回退。

  • 想撤销最近一次 commit 但保留所有改动在暂存区里，使用--soft：
1git reset --soft HEAD^1
  • 回退到指定的提交【注意】代码会丢失：
1git reset --hard 提交ID

命令详解：

HEAD^ 表示上一个版本，即上一次的commit，也可以写成HEAD~1 如果进行两次的commit，想要都撤回，可以使用HEAD~2

命令 含义
-soft 不删除工作空间的改动代码 ，撤销commit，不撤销git add file。
–hard 删除工作空间的改动代码，撤销commit且撤销add，会导致本次改动的代码丢失。

另外一点，如果commit注释写错了，先要改一下注释，有其他方法也能实现，如：

1git commit --amend
2这时候会进入vim编辑器，修改完成你要的注释后保存即可。

补充：^ 和 ~ 的区别（什么时候会不同）

1git reset HEAD~1
2#或者
3git reset HEAD^

虽然在这个场景下一样，但它们语义上有区别：

写法 含义
HEAD~1 往回数 1 代（线性回退）
HEAD^1 当前 commit 的 第 1 个父提交
HEAD^2 当前 commit 的 第 2 个父提交（仅 merge commit 有）

对于非 merge commit：HEAD^ == HEAD~1 == HEAD^1 对于merge commit：HEAD^ == HEAD^1（第一个父提交），而 HEAD^2 是第二个父提交。

3. 已经push到运程仓库（代码回滚）

  1. 查看git提交日志，找到上次提交的信息，输入命令 git log (查看全部日志)或 git log -xx(查看最近xx条日志）
1# 查看最近的 commit 历史
2git log --oneline --graph -20
  1. 回滚到指定的版本（hard后面接的是上面标红的commit，也就是想回滚到的版本）
1# 回退到指定版本，不保留原更改代码
2git reset --hard i7j8k9l
3
4# 回退到指定版本，保留原更改代码，且生成新的提交
5git revert i7j8k9l
  1. 强制提交（这个时候已经将代码回退了，你现在的分支状态就处于你上一步指向的版本）
1git push origin main --force-with-lease

如果你只是误提了代码，想保留代码改动的话，那就在第二步的时候使用revert 命令，而不是reset ,两者区别如下：

  • revert是放弃指定提交的修改，但是会生成一次新的提交，需要填写提交注释，以前的历史记录都在；
  • reset是指将HEAD指针指到指定提交，历史记录中不会出现放弃的提交记录。

清理历史记录

核心思路是用 git reset 或 git rebase 直接重写历史，把这几个 commit 彻底抹掉。

1# 1. 先确认要回退到的目标 commit（merge 之前的那个）
2git log --oneline
3
4# 2. 假设 i7j8k9l 是 merge 之前的最后一个正常 commit
5# 先创建备份分支（保险）
6git branch backup-before-cleanup
7
8# 3. 强制回退到 merge 之前
9git reset --hard i7j8k9l
10
11# 4. 如果已经 push 到远程，需要强制推送
12git push origin main --force-with-lease

强制推送覆盖远程分支的安全性

尽可能不使用git push -f origin main（或 --force）

行为：无条件用本地 main 覆盖远程 main，不管远程在此期间有没有被别人更新过。

风险：如果同事在你 pull 之后、你 push 之前向远程 main 推送了新 commit，你的强制推送会直接抹掉他们的工作。

而是使用：

1git push origin main --force-with-lease

行为：在强制推送前，先检查远程 main 是否还是你上次看到的样子。

  • 如果远程没变 → 推送成功
  • 如果远程已被别人更新 → 拒绝推送，提示你先 pull 合并

本质：它带有一个"租约"（lease），只有远程引用值与本地记录的远程跟踪分支（origin/main）一致时才允许强制覆盖。
